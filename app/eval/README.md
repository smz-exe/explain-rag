# Quality Harness

An engineering regression and inspection harness for the query pipeline.
**This is not a benchmark** and its numbers are not presented as research
results — see [What the numbers do and do not mean](#what-the-numbers-do-and-do-not-mean).

## What it does

Runs a fixed, committed question set through the full query pipeline
(in-process, reranking enabled) and reports:

- **Retrieval hit rank** against the question's source paper — the one metric
  with real ground truth, because it holds *by construction* (see below)
- **Rank displacement** introduced by the cross-encoder reranker
- **Per-stage latency** (embedding / retrieval / rerank / generation /
  faithfulness verification), median and p90
- Faithfulness scores from the pipeline's own verifier, reported strictly as
  **signals** (they are LLM-judge outputs; see caveats)

## Question set construction

The set is generated by a deterministic, documented procedure
(`generate_questions.py`) and committed as `questions.json` with full
provenance (generation date, model, procedure):

1. Take every ingested paper, ordered by arXiv ID
2. Generate exactly one question from the paper's **abstract**, instructing
   the model to paraphrase, avoid the paper's distinctive phrasing, and never
   name the paper
3. Record the source `paper_id` as the question's ground-truth label

Because each question is derived from a known paper, "does the retrieved
top-k contain a chunk of that paper, and at what rank" is an objective
measurement — no judge involved.

## What the numbers do and do not mean

- **Hit rank / MRR** measure whether retrieval surfaces content from the
  *right paper*. They do not measure whether the specific chunks are the best
  possible ones — that would require chunk-level relevance labels, which do
  not exist here.
- **Abstract-derived questions are biased toward retrievability**: abstracts
  summarize the same content the chunks contain, so real user questions are
  likely harder. Treat absolute hit rates as an upper bound.
- **Reranking here reorders the retrieved top-k window; it does not expand
  it.** It therefore cannot change *whether* the source paper is in the top-k
  — only its rank within the window. The vector-vs-reranked comparison
  isolates exactly that ordering effect (both orderings come from a single
  run: `original_rank` vs `rank`).
- **Faithfulness scores are LLM-judge outputs** (Claude judging Claude) with
  no ground truth; they can be systematically wrong in either direction.
  They are recorded to watch for regressions between runs, not as evidence
  of answer quality.
- n = one question per paper. Large enough to catch regressions, far too
  small for statistical claims. Do not read two-decimal differences as real.

## Running

```bash
# One-time (or after corpus changes): regenerate the committed question set
uv run python -m src.adapters.inbound.cli.generate_questions --env-file .env.production

# Run the harness (writes eval/results/<date>.json, prints a markdown summary)
uv run python -m src.adapters.inbound.cli.quality_harness --env-file .env.production

# Smoke run
uv run python -m src.adapters.inbound.cli.quality_harness --env-file .env.production --limit 3
```

Each full run makes ~3 Claude API calls per question (generation + claim
decomposition + verification). It is a manual tool, deliberately not part
of CI.

Results are committed under `results/` so runs are comparable over time;
each file records the model, embedding model, and question-set version it
ran against.
